# ADR-004 — Seguridad, autenticación y roles

## 1. Información general

| Campo | Valor |
|---|---|
| Identificador | ADR-004 |
| Proyecto | Costumes |
| Fecha | 11/11/2026 |
| Versión | 1.0 |
| Estado | Aceptada |
| Categoría | Seguridad y control de acceso |

## 2. Contexto

Costumes requiere controlar el acceso a las operaciones disponibles en la aplicación.

El sistema cuenta con dos roles operativos: `admin` y `advisor`. Cada uno dispone de permisos diferentes sobre las funcionalidades del sistema.

El administrador puede realizar operaciones administrativas como gestionar el catálogo, crear asesores y consultar reportes. Los asesores pueden participar en las operaciones correspondientes a clientes, alquileres, devoluciones y consultas permitidas.

Los clientes no se autentican en la aplicación.

La solución también debe proteger las credenciales almacenadas y evitar que información sensible, como contraseñas, hashes o secretos, sea expuesta mediante las respuestas de la API.

## 3. Problema

El sistema necesita un mecanismo que permita:

- Autenticar a los operadores.
- Identificar el rol del usuario autenticado.
- Restringir las operaciones según el rol.
- Evitar almacenar contraseñas en texto plano.
- Evitar la creación de administradores desde la API.
- Proteger los endpoints que requieren autenticación.
- Evitar que las respuestas expongan contraseñas, hashes, claves o secretos.

Sin estos controles, un usuario podría acceder a operaciones para las cuales no tiene autorización o información sensible podría quedar expuesta.

## 4. Decisión

Se utilizarán tokens JWT firmados para autenticar las solicitudes realizadas a la API.

Los tokens tendrán una duración de ocho horas.

La autenticación utilizará el esquema:

`Authorization: Bearer <token>`

Las contraseñas se almacenarán mediante hash utilizando Argon2id y nunca se conservarán en texto plano.

Se establecen dos roles:

| Rol | Responsabilidad |
|---|---|
| `admin` | Administración del sistema y acceso a las operaciones reservadas al administrador. |
| `advisor` | Operación de las funcionalidades permitidas para los asesores. |

El usuario `admin` inicial se crea únicamente utilizando variables de entorno durante la preparación del sistema.

La API no permitirá crear nuevos usuarios con rol `admin`.

Los nuevos usuarios `advisor` serán creados mediante la API por un usuario autenticado con rol `admin`.

El endpoint de inicio de sesión y el endpoint de salud podrán utilizarse sin autenticación. Las demás operaciones protegidas requerirán un token válido y, cuando corresponda, el rol necesario.

## 5. Manejo de autenticación y autorización

Cuando las credenciales sean correctas, el inicio de sesión devolverá un JWT junto con la información necesaria sobre su vigencia y rol.

Un token tendrá una vigencia de:

`8 horas = 28.800 segundos`

Cuando una operación protegida se realice sin autenticación válida, la API responderá con:

`401 Unauthorized`

Cuando un usuario autenticado intente realizar una operación para la cual su rol no tiene autorización, la API responderá con:

`403 Forbidden`

Los mensajes presentados al usuario deben mantenerse en español.

## 6. Administración de credenciales

Las contraseñas serán procesadas utilizando Argon2id antes de almacenarse.

No se debe incluir en las respuestas de la API:

- Contraseñas.
- Hashes de contraseñas.
- Secretos utilizados para firmar tokens.
- Claves internas.
- Información sensible de configuración.

El administrador inicial obtendrá sus credenciales desde variables de entorno.

Los secretos utilizados por el sistema no deben incorporarse directamente al código fuente.

## 7. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Almacenar las contraseñas en texto plano | Expondría directamente las credenciales en caso de acceso no autorizado a los datos. |
| Almacenar los tokens en la base de datos | Se opta por JWT firmado con vigencia limitada sin mantener cada token como una sesión persistente. |
| Permitir el registro público de administradores | Permitirá crear usuarios con privilegios elevados sin el control correspondiente. |
| Permitir crear administradores mediante la API | El rol administrativo debe provisionarse desde el entorno y no asignarse mediante las operaciones normales de usuarios. |
| Controlar los permisos únicamente desde React | Las solicitudes pueden realizarse directamente contra la API, por lo que la autorización debe aplicarse en el backend. |

## 8. Justificación

El uso de JWT permite autenticar las solicitudes realizadas a la API mediante tokens firmados y con una vigencia definida.

La duración de ocho horas limita temporalmente la validez de las credenciales de acceso.

Argon2id permite evitar el almacenamiento de contraseñas en texto plano.

La separación entre los roles `admin` y `advisor` permite restringir las operaciones según las responsabilidades de cada operador.

Crear el administrador inicial desde variables de entorno evita exponer una operación de registro administrativo mediante la API.

La creación de asesores queda bajo control del administrador, evitando que un usuario pueda asignarse por sí mismo privilegios administrativos.

## 9. Revocación de tokens

Los JWT emitidos no se almacenan como sesiones individuales en la base de datos.

Por esta razón, un token deja de ser válido cuando:

- Alcanza su fecha de vencimiento.
- Cambia el secreto utilizado para verificar su firma.

Esta decisión evita mantener una tabla de sesiones o tokens activos, aunque implica que no existe revocación individual inmediata de un token antes de su vencimiento.

## 10. Consecuencias

### Consecuencias positivas

- Las contraseñas no se almacenan en texto plano.
- Los endpoints protegidos requieren autenticación.
- Los permisos pueden controlarse según el rol.
- El rol `admin` no puede asignarse mediante la API.
- Los asesores son creados bajo control administrativo.
- Los tokens tienen una vigencia limitada.
- La API evita exponer credenciales y secretos en sus respuestas.

### Consecuencias y consideraciones

- El frontend debe enviar el token en las solicitudes protegidas.
- Los tokens vencidos requieren una nueva autenticación.
- La autorización debe verificarse en el backend y no depender únicamente de la interfaz.
- Un JWT emitido no puede revocarse individualmente antes de su vencimiento con el mecanismo seleccionado.
- Cambiar el secreto de firma invalida los tokens existentes.
- Los secretos y credenciales administrativas deben configurarse correctamente mediante variables de entorno.

## 11. Verificación

La decisión debe comprobarse mediante pruebas automatizadas que permitan verificar, como mínimo:

- Una solicitud sin autenticación recibe HTTP `401`.
- Una operación realizada con un rol sin autorización recibe HTTP `403`.
- Las credenciales inválidas reciben HTTP `401`.
- Un `advisor` no puede crear usuarios con rol `admin`.
- Las contraseñas se almacenan mediante hash.
- Las respuestas de la API no contienen contraseñas ni hashes.
- Los secretos de configuración no aparecen en las respuestas.
- El token emitido tiene una vigencia de ocho horas.

## 13. Resultado

Costumes utilizará JWT firmado con una vigencia de ocho horas para autenticar a sus operadores.

Las contraseñas se almacenarán mediante Argon2id. El administrador inicial se creará únicamente desde variables de entorno y los asesores serán creados mediante la API por un administrador.

Las operaciones protegidas verificarán autenticación y autorización en el backend, utilizando HTTP `401` para problemas de autenticación y HTTP `403` cuando el rol no tenga autorización.

Este registro establece la decisión de seguridad y control de acceso utilizada por el sistema.
