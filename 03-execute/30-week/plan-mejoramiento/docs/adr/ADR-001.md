# ADR-001 — Propiedad del esquema de base de datos

## 1. Información general

| Campo | Valor |
|---|---|
| Identificador | ADR-001 |
| Proyecto | Costumes |
| Fecha | 11/11/2026 |
| Versión | 1.0 |
| Estado | Aceptada |
| Categoría | Persistencia y migraciones |

## 2. Contexto

Costumes utiliza una base de datos PostgreSQL para almacenar la información relacionada con categorías, trajes, clientes, operadores, alquileres y líneas de alquiler.

El sistema se ejecuta mediante contenedores y la infraestructura es responsable de iniciar los servicios necesarios para su funcionamiento.

Sin embargo, es necesario establecer un único mecanismo responsable de crear y modificar la estructura de la base de datos para evitar que existan diferentes definiciones del mismo esquema.

## 3. Problema

Permitir que tanto la infraestructura como la aplicación creen o modifiquen tablas puede producir inconsistencias entre el esquema esperado por Laravel y el esquema realmente existente en PostgreSQL.

También dificultaría conocer:

- Qué versión del esquema está instalada.
- Qué modificaciones se realizaron.
- En qué orden deben aplicarse.
- Qué restricciones pertenecen al modelo de datos.
- Qué mecanismo constituye la fuente de verdad del esquema.

Por esta razón, debe existir un único propietario de la creación y evolución de la estructura de datos.

## 4. Decisión

Las migraciones de Laravel serán la única fuente autorizada para crear y modificar el esquema de la base de datos.

Los archivos ubicados en:

`api/database/migrations/`

serán responsables de definir:

- Tablas.
- Columnas.
- Claves primarias.
- Claves foráneas.
- Restricciones.
- Índices.
- Reglas de integridad implementadas en la base de datos.
- Datos estructurales requeridos, como las categorías iniciales.

La infraestructura será responsable únicamente de iniciar PostgreSQL y proporcionar la configuración necesaria para que la API pueda conectarse.

La carpeta `infra/` no debe contener instrucciones `CREATE TABLE` ni mantener una segunda definición del esquema.

Al iniciar una base de datos vacía, Laravel ejecutará sus migraciones para construir la estructura requerida por Costumes.

## 5. Responsabilidades

### Laravel

Laravel será responsable de:

- Crear el esquema.
- Ejecutar las migraciones.
- Mantener el historial de cambios.
- Crear las restricciones necesarias.
- Definir las relaciones entre las tablas.
- Incorporar los datos estructurales definidos por el sistema.

### Infraestructura

La infraestructura será responsable de:

- Iniciar PostgreSQL.
- Configurar el servicio de base de datos.
- Proporcionar las variables necesarias para la conexión.
- Permitir que la API ejecute las migraciones.

La infraestructura no debe duplicar la definición del esquema.

## 6. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Crear las tablas mediante scripts SQL en `infra/` | Duplicaría la definición mantenida por Laravel y podría generar diferencias entre ambos esquemas. |
| Mantener migraciones Laravel y scripts SQL simultáneamente | Existirían dos fuentes de verdad para la misma estructura. |
| Crear las tablas manualmente | No existiría un historial reproducible de los cambios realizados. |
| Crear el esquema implícitamente desde el código de la aplicación | Dificultaría controlar y verificar la evolución de la base de datos. |

## 7. Justificación

Las migraciones permiten mantener la evolución del esquema junto con el código de la API.

Utilizar un único mecanismo evita duplicar definiciones y facilita reproducir la estructura de datos cuando el sistema se ejecuta sobre una base PostgreSQL vacía.

También permite verificar de manera explícita qué tablas, restricciones e índices necesita la aplicación.

Esta decisión mantiene separadas las responsabilidades: la infraestructura inicia el servicio de base de datos y Laravel administra su estructura.

## 8. Consecuencias

### Consecuencias positivas

- Existe una única fuente de verdad para el esquema.
- Se evita duplicar SQL entre `api/` e `infra/`.
- Los cambios estructurales quedan registrados mediante migraciones.
- Una base de datos vacía puede prepararse de forma reproducible.
- Las restricciones de integridad quedan versionadas junto con la API.
- Se facilita verificar la estructura utilizada por el sistema.

### Consecuencias y consideraciones

- Todo cambio estructural debe realizarse mediante una nueva migración.
- La API debe poder conectarse correctamente a PostgreSQL antes de ejecutar las migraciones.
- `infra/` no debe incorporar scripts que creen las mismas tablas.
- Las migraciones deben conservar coherencia con `data-model.md`.
- Las restricciones implementadas en PostgreSQL deben coincidir con las reglas documentadas.

## 9. Verificación

La decisión se puede comprobar mediante:

1. Revisar que `infra/` no contenga instrucciones `CREATE TABLE` para crear el esquema de Costumes.
2. Iniciar PostgreSQL sin las tablas de la aplicación.
3. Ejecutar las migraciones de Laravel.
4. Verificar que las tablas y restricciones requeridas hayan sido creadas.
5. Consultar el estado de las migraciones mediante:

`php artisan migrate:status`

La estructura resultante debe corresponder con el modelo definido para Costumes.

## 11. Resultado

Costumes utilizará exclusivamente las migraciones de Laravel para crear y modificar el esquema de PostgreSQL.

La infraestructura iniciará la base de datos sin mantener una definición paralela de sus tablas.

De esta manera, `api/database/migrations/` se mantiene como la fuente de verdad para la estructura y evolución de la base de datos.
