## 2. Contexto

Costumes requiere un sistema para gestionar el alquiler y la devolución de trajes y disfraces.

La solución debe permitir administrar asesores, clientes, categorías, trajes, alquileres, devoluciones, disponibilidad y el reporte de trajes más solicitados.

Para organizar el desarrollo se requiere una arquitectura que permita separar las responsabilidades de la interfaz de usuario, la lógica de negocio, la persistencia de datos y la infraestructura.

También es necesario mantener una comunicación definida entre los componentes y garantizar que las reglas de negocio sean aplicadas de manera consistente.

## 3. Problema

Se necesita establecer una arquitectura y seleccionar las tecnologías que permitan desarrollar el sistema manteniendo separadas las responsabilidades de cada componente.

La interfaz de usuario no debe acceder directamente a la base de datos ni ser la única responsable de validar reglas como:

- El máximo de cinco trajes sin devolver por cliente.
- El plazo de alquiler de cuatro días.
- El bloqueo de clientes con alquileres vencidos.
- El control de las unidades disponibles.
- La conservación de la información histórica.
- El control de operaciones concurrentes sobre la última unidad disponible.

Estas reglas requieren un punto central de validación antes de modificar la información almacenada.

## 4. Decisión

Se adopta una arquitectura cliente-servidor con separación de responsabilidades entre los principales componentes del sistema.

| Componente | Tecnología | Responsabilidad |
|---|---|---|
| Frontend | React | Interfaz de usuario y presentación de información. |
| Backend | PHP y Laravel | API, validaciones y reglas de negocio. |
| Base de datos | Base de datos del sistema | Persistencia de la información. |
| Comunicación | HTTP y JSON | Intercambio de información entre frontend y backend. |
| Infraestructura | Contenedores | Ejecución integrada de la aplicación y la base de datos. |
| Sitio público | Sitio estático | Presentación pública de Costumes. |
| Herramientas | Cliente de la API | Sembrado de información mediante la API. |

El frontend consumirá los endpoints definidos en `api-contract.md` y no accederá directamente a la base de datos.

El backend será responsable de recibir las solicitudes, validar los datos, aplicar las reglas de negocio y realizar las operaciones correspondientes sobre la información persistente.

Las reglas de negocio se centralizarán en el backend para mantener un comportamiento consistente independientemente de la interfaz desde la cual se realice una operación.

La infraestructura permitirá iniciar los servicios y la base de datos con un solo comando.

El sembrado de datos se realizará mediante la API.

## 5. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Permitir acceso directo del frontend a la base de datos | Eliminaría la separación entre presentación, lógica de negocio y persistencia, además de dificultar la aplicación centralizada de las reglas. |
| Implementar las reglas únicamente en React | Las validaciones podrían evitarse mediante solicitudes realizadas directamente a la API. |
| Utilizar una tecnología diferente a PHP y Laravel para el backend | No corresponde con la tecnología establecida para el backend de Costumes. |
| Utilizar una tecnología diferente a React para el frontend | No corresponde con la tecnología establecida para la aplicación frontend. |
| Realizar el sembrado directamente sobre la base de datos | El sembrado de información se realizará mediante la API para utilizar las mismas operaciones y validaciones disponibles en el sistema. |

## 6. Justificación

La arquitectura seleccionada permite separar las responsabilidades del sistema y mantener la lógica de negocio centralizada.

React se utiliza para construir la interfaz con la que interactúan los usuarios, mientras que Laravel procesa las solicitudes, aplica las validaciones y ejecuta las reglas de negocio.

La comunicación mediante HTTP y JSON permite que el frontend consuma las operaciones proporcionadas por la API sin acceder directamente a la persistencia.

La separación también permite que el sembrador de datos utilice la API como mecanismo de comunicación.

La infraestructura basada en contenedores permite integrar la aplicación y la base de datos dentro de un entorno reproducible.

Esta decisión mantiene correspondencia con la especificación, la arquitectura, el modelo de datos y el contrato de API definidos para Costumes.

## 7. Consecuencias

### Consecuencias positivas

- Separación de responsabilidades entre interfaz, backend y persistencia.
- Centralización de las reglas de negocio.
- Comunicación definida mediante la API.
- El frontend no necesita acceso directo a la base de datos.
- El sembrador puede utilizar las mismas operaciones proporcionadas por la API.
- Los componentes pueden probarse de manera independiente.
- La infraestructura permite integrar los servicios necesarios para ejecutar el sistema.

### Consecuencias y consideraciones

- El frontend depende de la disponibilidad de la API para consultar y modificar información.
- Los cambios realizados en los endpoints deben mantenerse congruentes con `api-contract.md`.
- La lógica de negocio debe permanecer centralizada en el backend.
- Los servicios requieren una configuración correcta para comunicarse dentro del entorno de ejecución.
- Los cambios en la estructura de persistencia deben mantenerse coordinados con los modelos y migraciones del backend.

## 9. Resultado

Se establece una arquitectura cliente-servidor en la que React proporciona la interfaz de usuario y Laravel centraliza la API y las reglas de negocio.

Los componentes deben mantener las responsabilidades y mecanismos de comunicación definidos en este registro y en los documentos técnicos relacionados.

Este registro documenta una decisión de arquitectura y no constituye evidencia de que todos los componentes se encuentren implementados o funcionando.
