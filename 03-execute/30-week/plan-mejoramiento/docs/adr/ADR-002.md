# ADR-002 — Control de concurrencia en alquileres

## 1. Información general

| Campo | Valor |
|---|---|
| Identificador | ADR-002 |
| Proyecto | Costumes |
| Fecha | 11/11/2026 |
| Versión | 1.0 |
| Estado | Aceptada |
| Categoría | Integridad y concurrencia |

## 2. Contexto

Costumes administra trajes que cuentan con una cantidad total de unidades y una cantidad de unidades disponibles para alquiler.

Cuando se registra un alquiler, la disponibilidad del traje disminuye. Cuando se registra una devolución válida, la disponibilidad correspondiente se recupera.

El sistema debe garantizar en todo momento que las unidades disponibles permanezcan entre cero y el total de unidades.

Existe un escenario crítico cuando dos asesores intentan alquilar simultáneamente la última unidad disponible de un mismo traje.

## 3. Problema

Si dos solicitudes consultan la disponibilidad de manera simultánea y ambas detectan una unidad disponible antes de que alguna actualice la información, las dos podrían intentar confirmar el alquiler.

Esto podría provocar:

- Dos alquileres sobre una misma unidad disponible.
- Disponibilidad negativa.
- Inconsistencia entre el inventario y las operaciones registradas.
- Incumplimiento de las reglas de negocio.

Por lo tanto, consultar la disponibilidad antes de registrar el alquiler no es suficiente. La validación y actualización deben ejecutarse de manera controlada.

## 4. Decisión

El backend será responsable de controlar la concurrencia durante el registro de alquileres.

La comprobación de disponibilidad y su actualización se realizarán como parte de una operación controlada sobre los datos involucrados.

Para la última unidad disponible, el comportamiento esperado será:

| Solicitud | Resultado |
|---|---|
| Primera operación que obtiene la unidad | Alquiler registrado — HTTP `201` |
| Operación concurrente que ya no encuentra disponibilidad | Alquiler rechazado — HTTP `409` |

La disponibilidad debe cumplir siempre:

`0 <= available_units <= total_units`

La operación que no pueda obtener la unidad no debe generar un alquiler válido ni disminuir nuevamente la disponibilidad.

El control se implementará en el backend, evitando depender de validaciones realizadas únicamente desde la interfaz de usuario.

## 5. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Validar la disponibilidad únicamente en React | Dos usuarios pueden realizar solicitudes simultáneas y el frontend no controla el estado compartido de la base de datos. |
| Consultar disponibilidad y actualizarla como operaciones independientes sin control de concurrencia | El estado puede cambiar entre la consulta y la actualización. |
| Permitir disponibilidad negativa y corregirla posteriormente | Generaría operaciones inválidas y pérdida de integridad en el inventario. |
| Rechazar todas las solicitudes simultáneas | Una de las solicitudes puede completarse correctamente si todavía existe una unidad disponible. |

## 6. Justificación

El control de concurrencia en el backend permite que la disponibilidad real sea verificada en el momento de registrar la operación.

Esto garantiza que dos solicitudes no puedan utilizar simultáneamente la misma última unidad.

La decisión también permite mantener la disponibilidad dentro de los límites establecidos y proporcionar una respuesta clara a la operación que no pueda completarse.

El código HTTP `409` permite indicar que la solicitud entra en conflicto con el estado actual del recurso, mientras que la operación que obtiene correctamente la unidad responde con `201`.

## 7. Consecuencias

### Consecuencias positivas

- Evita alquileres duplicados sobre la última unidad.
- Impide que la disponibilidad sea negativa.
- Mantiene la consistencia entre alquileres e inventario.
- Centraliza el control de concurrencia en el backend.
- Permite informar claramente el conflicto mediante HTTP `409`.
- El comportamiento puede verificarse mediante pruebas automatizadas.

### Consecuencias y consideraciones

- El registro de alquiler debe controlar conjuntamente la validación y modificación de disponibilidad.
- Las pruebas deben incluir solicitudes concurrentes sobre la última unidad.
- La aplicación frontend debe manejar correctamente una respuesta `409`.
- Una operación rechazada por falta de disponibilidad no debe dejar cambios parciales en el sistema.

## 9. Resultado

El registro de alquileres debe proteger la disponibilidad ante solicitudes simultáneas.

Cuando dos operaciones intenten alquilar la última unidad al mismo tiempo, solamente una podrá completarse con HTTP `201` y la otra será rechazada con HTTP `409`.

La disponibilidad nunca podrá quedar por debajo de cero.

Este registro define la decisión de diseño para el manejo de concurrencia y debe mantenerse coherente con la implementación y las pruebas del sistema.
